## 1. 业务全景

**解决的核心问题**：SPU 定义「有哪些销售维度与候选值」（颜色、版本），但不承载价格与库存。真实交易中价格/库存随**规格组合**变化，因此需要「可下单的最小库存单位」—— SKU = 每个维度取一个值的组合。

**核心不变量**（I1~I11，完整表述见设计文档 §2.2）：

- **I1** 提交集合恰好等于笛卡尔积：无缺失、无多余、无重复（不可售组合用 `isSale=false` 表达，结构性缺口不允许）
- **I4** 同一 SPU 下组合唯一（复合唯一索引，并发兜底）
- **I8** 组合创建后不可变（组合是 SKU 的身份）
- **I11** 上架必须已定价（`price > 0`；生成 = 建结构，上架 = 营业）

**数据流向**：

```
SPU 列表行内「SKU」按钮 → /product/spu/sku?spuId=xxx（子路由，侧边栏无入口）
  → GET /spu/:id 取上下文（维度/首图/名称）+ GET /sku 分页列表（期望 M/实际 N 完整性提示）
  → 未生成：笛卡尔积生成表单（价格可留空=未定价）→ POST /sku 整组生成（I1 恰好覆盖）
  → 已生成：上下架开关 / 编辑弹窗（组合只读）/ 清空重建（DELETE 清空 + 再生成）
  → 后端校验流水线（服务端自己算期望集合，不信任客户端）→ 落库 → 11000 → 409
```

## 2. 技术实现链路（调用栈追踪）

**前端侧**（页面私有状态 + 全局 keep-alive，无 Pinia 参与 SKU 数据流）：

1. `watch(spuId)` 自洽：无 spuId → `router.replace('/product/spu')`（子页面语义）；切换 spuId → 重置上下文 + 并行拉 SPU 与 SKU 列表（请求序号防竞态）
2. 生成表单：先算乘积数（R19 防 OOM）→ 笛卡尔积建行 → 统一行级校验（重量/库存边界 + 上架闸门）→ 元→分字符串换算 → 一次 POST
3. 列表：组合 tag / 价格 `centsToYuan` / 上下架开关（未定价拦截 + 绿/橙反馈）→ PATCH；图片回退 SPU 首图
4. 编辑弹窗（destroy-on-close）：白名单字段 + 组合只读回显；价格换算 + 上架闸门

**后端侧**（四层流水线，与 SPU 模块同构）：

```
routes/sku.ts           auth → 路由声明
controllers/sku.ts      形状校验：spuId/items 数组/每项 skuSaleAttrValueList 数组/数值类型
services/sku.ts         ①ensureSpu → ②已有 SKU 409 → ③清洗 + ③b 单行结构
                        → ④乘积数预检 → ⑤笛卡尔积 → ⑥维度集合 == → ⑦取值 ∈ 候选
                        → ⑧集合比对（重复/缺失/多余）→ ⑨派生（I3/R8/R15/R24）→ ⑩数值边界 + I11 闸门
                        → 按 combinationKey 排序 → insertMany(ordered)
models/Sku.ts           复合唯一索引 (spuId, combinationKey) → 11000 → 409；validator 兜底
```

## 3. 架构决策分析

**① 整组生成 vs 单条添加（本模块的一号决策）**：以「必定生成全部组合 + `isSale` 控制可售性」换取**可结构校验的完整性**。单条添加无法区分「漏填」与「停产」；矩阵完整才能让 I1 成立。真实大厂的停产/清仓同样是「组合保留 + 状态不可售」，与 `isSale=false` 同构。

**② `combinationKey`：码点排序 + JSON + sha256**。排序用码点比较而非 `localeCompare`（ICU 数据随环境变化 → 同一组合在不同机器键不一致 → 唯一索引**静默失效**，比报错更危险）；hash 固定 64 字符，键长与维度数解耦。

**③ 先算乘积数、后物化（R26）**：10 维 × 20 值 = 20¹⁰ ≈ 1e13，先物化再检查会 OOM。④ 预检在物化前拦截（期望数与提交数两侧），⑤ 才展开笛卡尔积。边界测试里有防 OOM 回归用例（15×15=225 快速 400，顺序颠倒即挂起）。

**④ 价格存「分」+ 前端字符串换算（R21）**：整数分消灭浮点误差；`19.99 * 100 = 1998.999…` 这类边界靠字符串解析规避。展示只 `toFixed` 不回算。

**⑤ 唯一索引 vs 先查后写**：`(spuId, combinationKey)` 复合唯一索引做并发兜底；写入前按 combinationKey 排序保证并发双 POST 后到方第 1 条即冲突、0 残留。

**⑥ 清空整组 vs 删单条（R14）**：I1 的库内形态只有两种合法状态——恰好完整或不存在。删单条会打回「部分组合」；单组合停售走 `isSale=false`，结构性移除只能整组撤销。

**⑦ 组合不可变（I8）**：组合是 SKU 的身份，PATCH 白名单不含组合字段——改组合等于变相 delete+create，且会让 I1/I4 的保证失效。

**⑧ 上架闸门（I11，v0.9 定案）**：生成时价格可留空（`price=0` = 未定价，草稿语义），上架时必须有价。后端双入口校验（PATCH 生效价 + 生成逐行）+ 前端三层拦截。库存不设门槛（无扣减逻辑的死属性）。

**⑨ 分层落地**：后端按「数据结构一步到位 → 信任版 CRUD → I1→I2→I5/I9→I4→I6/I7→I11 逐层补齐」实施，每层带该层的边界用例。收益：每一道校验的「为什么」都是亲手体会过的（如先被重复组合坑一次，才懂唯一索引的 409），面试时每层都是可讲的结论。

**⑩ 复杂度控制（R27/R28）**：砍 PUT 整组替换（重建回归两步）、砍补偿回滚（失败即整体失败 + 完整性提示兜底）、5.2 压缩至要点级、豁免实现手册。后端复杂度回到 SPU 模块水位，「前端主导、后端够用」的形态。

**⑪ 子路由 + keep-alive（状态保留定案）**：SKU 是 SPU 的子页面（`/product/spu/sku`，侧边栏无入口，无 spuId 重定向回父页）。SPU 列表页 keep-alive 缓存（`include: ['Spu']` + 组件 `defineOptions` 对齐 + `:key="route.fullPath"` + keep-alive 绑 refresh 作 key 保证刷新清缓存），`onActivated` 激活时刷新列表。**实验记录**：单分支无 key → 白屏（异步组件卡过渡进场，历史「空白 bug 三连」）；双分支双 transition → 状态丢失 + 切换跳动；最终结构为用户亲测定案。

## 4. 关键函数深度拆解

### `generateSkus`（services/sku.ts）

- **入参设计**：`(spuId, items)`——items 已经 controller 形状校验，service 收到「字段已确认存在」的输入，聚焦业务规则
- **边界处理**：流水线 ③~⑩ 每一步一个明确 400 与专属文案；**校验前置（I10）**——全部通过才触碰数据库，任何 400 都不产生半批写入
- **返回值设计**：生成后的 DTO 列表（与各模块 create 返回 DTO 的惯例一致）；`combinationKey` 不进 DTO
- **副作用**：唯一副作用是 insertMany；失败路径（11000）转 409 而非 500

### `updateSku`（services/sku.ts）

- **入参设计**：`(id, updates)`——白名单逐字段挑拣，白名单外一律忽略（防过度赋值）
- **边界处理**：上架闸门取**生效价**（patch 带新价用新价，否则查库里现值）——「定价与上架同请求」是编辑弹窗的常态，必须放行
- **返回值设计**：更新后的 DTO；空 patch → 400「没有需要更新的字段」（误导性成功比错误更糟）

### `combinationKeyOf` / `deriveSkuName`（services/sku.ts）

- 组合键：码点排序 + JSON + sha256，纯函数、环境无关、可测试
- 派生名：按 **SPU 声明顺序**拼接（码点排序只服务于键的去歧义，名称要业务可读）；截断时**组合值优先保留**（组合是 SKU 间的区分信息，SPU 名是冗余上下文）

### 前端 `generate-form`

- 组合数先算乘积数拦截（与后端 ④ 同规则）；行级校验与后端镜像（双防线）；`yuanToCents` 字符串换算（R21）；上架闸门拦截（I11）

## 【风险提示】

1. **批量填价工具未做** —— 组合多时逐行填价仍是痛点。统一价（做过又按用户要求撤回）、Excel 导入（方案已讨论：模板下载 + 组合键匹配行 + 全量校验先于写入）、规格加价（淘宝式，明确不做）—— 均为待定项
2. **上架闸门只查价格** —— 真实平台的上架必填还包括主图、类目资质、审核流；按范围控制只做价格，将来加字段时闸门是单点扩展（后端一个 if 块）
3. **孤儿图片** —— 上传未提交的文件残留（全局问题，SPU 模块同款，风险表已记录）
4. **边界常量镜像靠人工同步** —— `SKU_LIMITS` 前后端各一份（键名一致）；漏改的后果是前端提示与后端拦截不一致（后端仍会拦）
5. **完整性提示的期望数前端算** —— `GET /api/sku` 未返回期望组合数，前端从 SPU 快照重算一遍（轻微重复，无一致性风险）
6. **无版本控制** —— 并发改价是 last-write-wins；无交易域场景可接受，接入订单域时需乐观锁

## 如果重构，我会改进…

1. **zod Phase 1 覆盖本模块** —— 生成请求是嵌套数组形状最复杂的接口，手写形状校验最长
2. **批量填价工具落地**（统一价最少、Excel 导入性价比最高）
3. **上架闸门抽成独立校验函数** —— 将来多入口（批量上架）时保证规则单点
4. **`GET /api/sku` 返回 `expectedCount`** —— 完整性提示由后端给，前端不算
5. **keep-alive 缓存列表从布局硬编码升级为路由 meta 驱动** —— 第二个需要缓存的页面出现时
