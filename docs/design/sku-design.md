## 1. 背景与目标

### 1.1 业务背景

SPU 描述"这是什么商品"（iPhone 15），但不承载价格与库存。价格、库存、图片随**规格组合**变化，因此需要"可下单的最小单位"——SKU。SKU 由 **SPU 的销售属性各取一个值**唯一确定。

### 1.2 本期目标

1. **整组生成**：按 SPU 的 `saleAttrList` 计算笛卡尔积，一次提交、一次落库，**组合恰好全覆盖**（缺一个都不允许）
2. 运营只需为每个组合填**价格 / 库存**（名称与图片可由后端派生 / 回退）
3. 引用完整性：SKU 存在时的 SPU 删除与销售属性变更策略；品牌引用检查
4. 组合唯一性：并发安全，且组合创建后不可变

### 1.3 非目标（明确不做）

| 不做的事 | 原因 |
|---|---|
| 库存扣减、订单、超卖控制 | 交易域；本期只存 `stock` 数值 |
| SKU 冗余平台属性快照 | 平台属性是 SPU 级共性；冗余会产生"SPU 改了 SKU 没改"的不一致 |
| 分类-品牌关联、类目销售规格池 | 与 SKU 无耦合（维度来自 SPU、品牌继承 SPU），留到分类管理 CRUD 批次 |
| **允许部分组合（子集 SKU）** | 本期**明确不允许**：完整性优于灵活性，见 1.4；不可售组合用 `isSale=false` 表达 |
| SKU 多图 | 本期只有 `skuDefaultImg` |
| 软删除 | 当前无历史订单需保留，软删除会让所有查询都带过滤条件 |
| 多文档事务 | 单机 mongod 不支持；用"校验前置 + 失败可见性"替代，见 5.2 |
| **整组替换接口（PUT）** | 曾设计（R20）后为控制复杂度砍掉（R27）；重建 = 清空 + 再 POST 两步，见 7 风险表 |

### 1.4 核心取舍：为什么"整组生成"（用冗余换完整性）

| | 整组生成（本期选定） | 单条添加（v0.1，已废） |
|---|---|---|
| 完整性 | **结构性保证**：不齐就提交不了 | 无法保证，可能出现"4 个组合只建了 1 个" |
| 脏数据风险 | 低 | 高（残缺组合是典型脏源） |
| 冗余 | 会生成暂时不可售的组合 | 无冗余 |
| 不可售组合怎么办 | `isSale=false` 表达"建了但不上架" | — |
| 与真实大厂差异 | 大厂可删除个别组合；本期的不可售组合用 `isSale=false` 表达（与真实系统的停产/下架同构：组合记录保留、状态不可售） | — |

**结论**：以"必定生成全部组合 + `isSale` 控制可售性"换取**可结构性校验的完整性**。这是有意识的取舍，不是不知道大厂怎么做——取舍理由必须能讲出来。

## 2. 领域模型

### 2.1 SPU / SKU 职责分工

| 维度 | SPU | SKU |
|---|---|---|
| 语义 | 商品 | 可下单的最小库存单位 |
| 组合 | 定义有哪些维度与候选值 | 每个维度取一个值 |
| 价格 / 库存 / 默认图 | 无 | **有** |
| 平台属性 | 有 | 无 |
| 上架状态 | 无 | `isSale` |

判断法则：**字段是否随"组合"变化**——会变的挂 SKU，不会变的挂 SPU。

### 2.2 核心不变量（Invariants）

| 编号 | 不变量 | 保障手段 |
|---|---|---|
| **I1** | 提交的 SKU 集合**恰好等于** `SPU.saleAttrList` 的笛卡尔积：无缺失、无多余、无重复（正常库内形态即"恰好完整或不存在"；写入中断的残缺态由 I10 兜底） | 服务端计算期望集合 + 集合比对 → 400 |
| I2 | 每行每个维度的取值 ∈ 该维度在 SPU 中的候选值 | service → 400 |
| I3 | `sku.category3Id` 恒等于 `spu.category3Id` | 服务端复制，不接受客户端传值 |
| I4 | 同一 SPU 下 `(spuId, combinationKey)` 唯一 | 复合唯一索引（并发兜底）→ 409 |
| I5 | `price` / `weight` / `stock` 为非负整数 | 模型 validator + service 400 |
| I6 | SPU 存在 SKU 时不可删除；`saleAttrList` 的**规范化形式发生变化**时不可修改（**同值放行**） | service 比对 → 409 |
| I7 | 品牌存在 SPU 引用时不可删除 | service → 409 |
| **I8** | SKU 的组合（`skuSaleAttrValueList`）创建后**不可变** | PATCH 白名单不含该字段 |
| **I9** | 单次生成的组合数 ≤ `MAX_COMBINATIONS` | service → 400 |
| **I10** | 批量写入失败后的**残缺组必须可见**（列表页「期望 M / 实际 N」完整性提示），且可通过清空重建恢复 | 完整性提示 + 清空重建（见 5.2） |
| **I11** | 上架（`isSale=true`）的 SKU 必须已定价（`price > 0`）；未定价只能下架 | service → 400「请先设置价格再上架」（PATCH 与生成双入口） |

**空维度边界（R9）**：`saleAttrList` 为空是合法的（一本书也是一个 SKU）。0 维笛卡尔积 = 含一个空组合的集合 → **恰好生成 1 个 SKU**，其 `combinationKey = sha256("[]")`。实现时不需要特判，笛卡尔积算法自然得到这个结果，但必须**显式写测试**。

## 3. 数据模型

### 3.1 `Sku` 集合字段

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `spuId` | ObjectId | required, ref Spu | 归属 |
| `category3Id` | ObjectId | required, ref Category | 服务端从 SPU 复制（I3） |
| `skuName` | String | required, trim, ≤100 | **服务端派生**，允许后续 PATCH 改名 |
| `price` | Number | required, 整数, 0 ≤ p ≤ `PRICE_MAX` | **单位：分** |
| `weight` | Number | required, 整数, 0 ≤ w ≤ `WEIGHT_MAX` | 单位：克 |
| `stock` | Number | required, 整数, 0 ≤ s ≤ `STOCK_MAX` | 不做扣减 |
| `skuDesc` | String | default '', trim, ≤500 | |
| `skuDefaultImg` | String | **default ''** | 为空时前端回退 SPU `imageList[0]` |
| `skuSaleAttrValueList` | 子文档数组 | `_id: false`，快照语义 | `{ saleAttrName, saleAttrValue }` |

| `createdAt` / `updatedAt` | Date | timestamps | |

### 3.2 `combinationKey`：确定性规范化 + sha256

```ts
// ① 规范化：按维度名做「码点排序」——与语言环境无关
//    禁止用 localeCompare：它依赖运行环境的 ICU 数据，同一组合在不同机器可能排出不同顺序，
//    导致 key 不一致 → 唯一索引静默失效（脏数据落库，比报错更危险）
function canonicalCombination(list: { saleAttrName: string; saleAttrValue: string }[]): string {
  const pairs = list.map((v) => [v.saleAttrName, v.saleAttrValue] as const)
  pairs.sort((a, b) => (a[0] < b[0] ? -1 : a[0] > b[0] ? 1 : 0))
  return JSON.stringify(pairs) // JSON.stringify 而不是自造分隔符：不重新发明序列化，且无分隔符歧义
}

// ② 压缩：sha256 → 固定 64 个 hex 字符（node:crypto 的 createHash）
const combinationKey = createHash('sha256').update(canonicalCombination(list)).digest('hex')
```

**为什么 hash（按重要性排序）**：

1. **确定性**：`canonicalCombination` 与环境无关（这是 hash 能成立的前提，也是 R3 的一号修复）
2. **碰撞**：sha256 碰撞概率可忽略；且 I1/I2 已在 service 层做过结构校验，hash 只承担"等价性判定"

**索引**：`skuSchema.index({ spuId: 1, combinationKey: 1 }, { unique: true })`
- 唯一性交给数据库索引（并发安全），而非"先查后写"
- 前缀即 `spuId`，"按 SPU 查列表"无需额外索引
- `combinationKey` **不出现在 DTO 中**（服务端实现细节）

### 3.3 价格单位：整数「分」

| 方案 | 优点 | 缺点 |
|---|---|---|
| **整数分（选定）** | 无浮点误差；求和不失真；为折扣/聚合铺路 | 前端需格式化与换算 |
| 浮点元 | 前端直观 | `0.1 + 0.2 !== 0.3`，金额聚合失真 |

字段名 `price`，**注释、接口契约、前端类型三处必须写明"单位：分"**，前端展示统一走格式化函数。

**前端换算规则（R21）**：输入单位是**元**，提交前转分。
- ❌ 不要 `Math.round(yuan * 100)` 直接乘浮点：`19.99 * 100 = 1998.9999…`，边界值会差 1 分
- ✅ 按字符串解析：`/^\d+(\.\d{1,2})?$/` 校验（拦截 >2 位小数、负数、科学计数法），再去掉小数点后左侧补零、右侧补足两位，拼成整数分
- 展示方向同理：`(cents / 100).toFixed(2)` 只用于显示，不参与回算

### 3.4 边界常量 `SKU_LIMITS`（唯一来源）

后端 `models/Sku.ts` 导出，模型 validator 与 service 共用；前端 `views/product/sku/constants.ts` 镜像（两个独立包不能共享代码）。**只镜像前端真正会拦截的键**（与 SPU 模块同一取舍）：

| 键 | 值 | 含义 | 前端是否镜像（R23） |
|---|---|---|---|
| `NAME_LENGTH` | 100 | `skuName` | ✅ 改名输入框 `maxlength` |
| `DESC_LENGTH` | 500 | `skuDesc` | ✅ 描述输入框 `maxlength` |
| `PRICE_MAX` | 999999900 | 价格上限（分） | ✅ 表单校验 |
| `WEIGHT_MAX` | 999999 | 重量上限（克） | ✅ 表单校验 |
| `STOCK_MAX` | 999999 | 库存上限 | ✅ 表单校验 |
| `MAX_DIMENSIONS` | 10 | 组合维度数（与 SPU `MAX_SALE_ATTR_COUNT` 对齐） | ❌ 维度来自 SPU 快照，无前端入口 |
| **`MAX_COMBINATIONS`** | **200** | **单 SPU 组合数上限（R12）** | ✅ 生成表单先算乘积数拦截（R19） |

**为什么必须设 `MAX_COMBINATIONS`**：SPU 允许 10 维度 × 每维 20 值 → 理论 20¹⁰ ≈ 1e13 组合。没有上限时，一次生成的笛卡尔积就能打满内存、写爆集合；**且检查必须先于物化**（先算乘积数 ∏值数，物化 1e13 个元素会先 OOM —— 见 5.1 ④）。200 覆盖真实电商（通常 2–3 维、几十个组合），超出即 400。

## 4. 接口契约

### 4.1 接口总表

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/api/spu/:id` | 需登录 | **新增（R7）**：SPU 详情，SKU 页刷新后取 SPU 上下文（名称、`saleAttrList`、图片） |
| GET | `/api/sku?spuId=&page=&pageSize=` | 需登录 | 按 SPU 分页查 SKU |
| POST | `/api/sku` | 需登录 | **首次整组生成**：该 SPU 当前无 SKU，否则 409（安全网） |
| PATCH | `/api/sku/:id` | 需登录 | 白名单：`skuName / price / weight / stock / skuDesc / skuDefaultImg / isSale`（**不含 `skuSaleAttrValueList`**，I8） |
| DELETE | `/api/sku?spuId=` | 需登录 | **清空该 SPU 的全部 SKU**（撤销生成，I1 库内完整性） |

**为什么没有"整组替换"接口（R27）**：重建 = 清空（DELETE）+ 再生成（POST），两步。曾引入 `PUT` 整组替换（R20），后为控制复杂度砍掉（v0.7），两步之间的数据丢失窗口转入 7 风险表（接受）。

**入口（R2）**：SKU 页**不自带下钻与 SPU 列表**。入口在 SPU 列表每行的「SKU」按钮 → 跳转 `/product/sku?spuId=xxx`；SKU 页凭 `spuId` 调 `GET /api/spu/:id` 取上下文渲染表头，再分页拉 SKU。页面刷新、直接粘贴 URL 都能自洽（这正是 R7 必须补的原因）。

### 4.2 请求 / 响应要点

**POST /api/sku（首次整组生成）**：

```jsonc
{
  "spuId": "…",                    // 必填，在请求体内
  "items": [                       // 必须恰好覆盖笛卡尔积
    {
      "skuSaleAttrValueList": [ { "saleAttrName": "颜色", "saleAttrValue": "黑色" },
                                { "saleAttrName": "版本", "saleAttrValue": "128G" } ],
      "price": 499900,             // 分；0 = 未定价（上架前必须定价，I11）
      "weight": 200,               // 克
      "stock": 10,
      "isSale": false,             // 可选，默认 false
      "skuName": "…",              // 可选；缺省由服务端派生
      "skuDefaultImg": ""          // 可选；缺省为空串，展示回退 SPU 首图
    }
    // …
  ]
}
```

- **`price = 0` 即「未定价」**：生成与 PATCH 均允许（生成时价格可留空）；`isSale=true` 时要求 `price > 0`（I11 上架闸门）
- **服务端不接受 `category3Id` 与 `combinationKey`**：按白名单**静默忽略**（R22，与 brand/spu 的既有惯例一致），不返回错误
- **`skuName` 派生规则（R8/R15/R24）**：`spu.name + ' ' + 各维度值`，维度顺序取 **`SPU.saleAttrList` 声明顺序**（码点排序只服务于 `combinationKey` 的去歧义，名称要业务可读）；截断时**组合值部分优先保留**——先给组合值部分留足长度，剩余长度给 SPU 名（若剩余不足则整体截断到 `NAME_LENGTH`）
- **`skuDefaultImg` 空** → 前端展示回退 `spu.imageList[0]`
- **成功响应**：返回**生成后的 SKU 列表**（与各模块 create 返回 DTO 的惯例一致，前端直接渲染，无需二次查询）

**PATCH /api/sku/:id**：只做"运营日常动作"——定价、改库存、上下架、改名、换默认图、改描述。**不接受组合字段**（I8）。

**DELETE /api/sku?spuId=xxx（清空整组，R14）**：先 `ensureSpu` 校验 SPU 存在（不存在 → 404），再 `deleteMany({ spuId })` 幂等清空（存在但无 SKU → 200 + `deletedCount: 0`）。

### 4.3 错误码矩阵

| 场景 | 码 | 消息要点 |
|---|---|---|
| 未登录 / token 失效 | 401 | 拦截器统一处理 |
| 缺 `spuId` / 缺 `items` | 400 | 必填参数缺失 |
| `spuId` 不存在 | 404 | SPU 不存在 |
| POST 时该 SPU 已有 SKU | 409 | 已有 SKU；如需重建请先清空再生成（两步） |
| 清空整组：缺 `spuId` / SPU 不存在 | 400 / 404 | 与查询同规则；SPU 存在但无 SKU 时幂等返回 200 |
| 组合**缺失** | 400 | 列出缺失的组合（维度取值） |
| 组合**多余** | 400 | 列出多余/非法组合 |
| 组合**重复**（提交内） | 400 | 指出重复的组合 |
| 单行**维度重复**（同一维度出现两次） | 400 | 维度重复，属请求结构错误（**不再静默去重**） |
| 维度数 ≠ SPU 维度数 / 维度名不认识 | 400 | 指出多余或缺失的维度名 |
| 取值不在候选内 | 400 | 指出"维度 X 的取值 Y 不在候选值中" |

| 删除有 SKU 的 SPU | 409 | 请先删除该 SPU 下的 SKU |
| 有 SKU 时**修改**SPU 销售属性（规范化形式变化） | 409 | 请先删除该 SPU 下的 SKU |
| 删除有 SPU 引用的品牌 | 409 | 该品牌下仍有 SPU |
| 非法 ObjectId / JSON 解析失败 | 400 | errorHandler 兜底 |

## 5. 关键流程

### 5.0 页面流转

```
/product/spu（SPU 列表）
   └─ 行内「SKU」按钮 ──► /product/sku?spuId=xxx
                              ├─ GET /api/spu/:id        → 表头上下文（名称/维度/首图）
                              ├─ GET /api/sku?spuId=…    → 分页表格（含"期望 M / 实际 N"完整性提示）
                              ├─ 无 SKU → POST  /api/sku（生成）
                              └─ 重建 → 清空 + 再 POST（二次确认）
```

### 5.1 整组生成校验流水线

```
routes/sku.ts        auth
controllers/sku.ts   形状校验：spuId 必填；items 是数组；每项含 skuSaleAttrValueList 数组；数值类型
services/sku.ts      ① ensureSpu(spuId)                                   → 404
                     ② 已有 SKU？                                              → 409
                     ③ 逐行规范化 skuSaleAttrValueList（trim；**不做去重**）
                        - 单行维度重复 / 空维度名 / 空值                    → 400
                     ④ 组合数预检（**先算数、不物化**）：
                        - 期望数 = ∏(各维度值个数)，纯乘法
                        - 提交数 = items.length
                        - 任一 > MAX_COMBINATIONS                          → 400（I9）
                        （10 维 × 20 值 = 20¹⁰ ≈ 1e13：先物化后检查会 OOM）
                     ⑤ 计算期望集合 = cartesian(SPU.saleAttrList)（④ 已保证 ≤ 200，物化安全）
                        - 组合数超限的 400 已在 ④ 前置拦截（物化前，防 OOM）
                     ⑥ 逐行维度集合 == SPU 维度集合                        → 400（I1/I2）
                     ⑦ 每行取值 ∈ 对应维度候选值                            → 400（I2）
                     ⑧ 计算 canonical + hash，做集合比对：
                        缺失 / 多余 / 提交内重复                            → 400（I1）
                     ⑨ 派生 skuName（缺省时）+ 截断；category3Id := SPU 值   （I3）
                     ⑩ 数值边界（整数/非负/上限）                            → 400（I5）
                     ── 以上全部通过才触碰数据库（I10）──
models/Sku.ts        ⑪ 按 combinationKey 排序 → insertMany({ ordered: true })
                     ⑫ 唯一索引 / validator 错误 → 409 / 400（见 5.2）
                     ⑬ 失败 → 整体失败；残缺组靠完整性提示暴露（见 5.2）    （I10）
```

**为什么校验在 service**：controller 只回答"请求形状对不对"，service 回答"业务上成不成立"；将来批量生成任务、测试直调 service 时规则依然生效。

### 5.2 批量写入的失败处理（要点版，R27/R28）

- 单机 mongod 无事务：`insertMany({ ordered: true })`，失败即整体失败，**不做补偿回滚**（按组合键删会误伤并发成功方、按 `_id` 删复杂度就回去了）

- 写入前按 `combinationKey` 排序文档数组：并发双 POST 顺序一致，后到方在第 1 条即 11000、0 残留

- 唯一索引冲突 → `isDuplicateKeyError`（增强版，覆盖 bulk 多错形状）→ 409；校验失败 → 400
- 极端中断可能留残缺组：列表页「期望 M / 实际 N」提示**暴露**，清空 + 再 POST 重建
- 环境事实依实测版本（mongoose 9.9.3 / mongodb 7.5.0），不凭旧版博客记忆

```ts
// isDuplicateKeyError 增强：现有实现只判顶层 err.code，bulk 多错形状会漏
const e = err as { code?: number; writeErrors?: Array<{ err?: { code?: number }; code?: number }> }
if (e.code === 11000) return true
return Array.isArray(e.writeErrors)
  && e.writeErrors.some((w) => (w?.err?.code ?? w?.code) === 11000)
```

### 5.3 上架 / 下架状态机

```
      PATCH { isSale: true }
未上架 ────────────────────────► 已上架
false  ◄──────────────────────── true
      PATCH { isSale: false }
   生成时默认 false
```

- 状态变更只经 `PATCH`；`DELETE` 是**清空整组**（撤销生成，R14），与上下架无关
- 接入交易域后，"已上架且有订单"需改为下架 + 软删（本期不做）

### 5.4 删除与引用完整性（I6 / I7 / I10）

| 操作 | 检查 | 结果 |
|---|---|---|
| 清空 SKU（`DELETE /api/sku?spuId=`） | 无下游引用 | 幂等清空（撤销生成）；单组合停售不删除，走 `isSale=false` |
| 删除 SPU | 存在 SKU | 409 |
| 修改 SPU `saleAttrList` | 存在 SKU **且规范化形式发生变化** | 409；**同值放行**（R5） |
| 删除品牌 | 存在 SPU 引用 | 409 |

**I6 的同值放行实现（R5）**：复用 3.2 的规范化思路——把 `saleAttrList` 规范化（维度按码点排序、值去重后排序）成确定性字符串比较；相等即视为"未变更"，放行；不等才 409。**否则 SPU 编辑弹窗永远带全量 `saleAttrList`，一有 SKU 连改名字都保存不了**。

**为什么删除是"清空整组"而不是删单条（R14）**：I1 的库内形态只有两种合法状态——恰好完整或不存在。删单条会把集合打回"部分组合"状态（正是 1.4 否掉的脏数据形态）；单组合的不可售由 `isSale=false` 表达。

**为什么没有"整组替换"接口（R27）**：v0.4 曾引入 `PUT` 替换（校验先于删除），后为控制复杂度砍掉 —— 重建回归「清空 + 再 POST」两步：清空成功后若生成失败，需重填整组（前端表单数据仍在，可复制重提）。重建是低频操作，此窗口**接受**（见 7 风险表）。

**为什么不做级联删除**：SKU 有独立价格与库存，不属于"天然从属、无独立价值"的子数据；级联会一次带走整条商品线且不可恢复。"删除前先问引用"把风险交回操作者。

## 8. 测试策略

- **不变量反向用例**：I1（缺/多/重组合）、I2（非法取值）、I5（负数/小数/超上限）、I6（改维度 409 / 同值放行 200）、I7（删被引用品牌 409）、I8（PATCH 组合字段被忽略）、I9（组合数超限 400）
- **边界用例**：空 `saleAttrList` → 恰好 1 个 SKU（`combinationKey = sha256("[]")`）；单维度单值 → 1 个组合；维度重复 → 400
- **组合数超限用例（I9，防 OOM 回归）**：构造 10 维 × 20 值的 SPU（理论 20¹⁰），生成请求必须**快速**返回 400 —— 验证「先算乘积数、后物化」的顺序（顺序颠倒此用例会 OOM/挂起）
- **清空用例（R14）**：清空后集合为空、可重新生成；清空无 SKU 的 SPU → 200 幂等；清空不存在的 SPU → 404
- **重建用例**：清空 → 再 POST 完整流程成功（两步）；清空幂等 / 不存在 404 见清空用例
- **并发用例**：同一 SPU 并发两次 POST → 恰好一组成功、另一组 409 且**不残留**（写入前按 `combinationKey` 排序，后到方第 1 条即冲突；验证 I4）
- **上架闸门用例（I11）**：未定价上架 → 400；定价与上架同请求 → 200；定价后再上架 → 200；生成时勾上架未定价 → 400
- **确定性用例**：同一组合在不同构造顺序下 `combinationKey` 相同（防止排序/ICU 回归）
- **错误映射用例**：构造 11000 → 断言 409 而非 500（验证 `isDuplicateKeyError` 对 bulk 错误形状生效）
